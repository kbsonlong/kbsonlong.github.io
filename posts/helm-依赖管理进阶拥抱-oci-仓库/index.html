Helm 依赖管理进阶：拥抱 OCI 仓库

刚才我们聊到了将依赖包打包到本地（存冰箱）来保证稳定性。但是，如果你觉得把一堆 .tgz 二进制文件塞进 Git 仓库太臃肿（Git 并不擅长管理二进制大文件），那么 OCI (Open Container Initiative) 仓库 就是你的终极解决方案。

1. 什么是 OCI 模式？

简单来说，就是像管理 Docker 镜像一样管理 Helm Charts。

  • 以前：Chart 必须放在 HTTP 服务器上，或者打包成文件。
  • 现在：Helm Chart 可以直接推送到支持 OCI 标准的镜像仓库（比如 Harbor、AWS ECR、Google GAR）。

比喻升级：

  • 本地打包：买菜存自家冰箱（占地方，Git 仓库变大）。
  • OCI 仓库：把菜存到小区的公共大冷库（内网 Harbor）。
    • 不占自家地：Git 仓库清爽，只存代码。
    • 内网高速：走内网拉取，速度极快，稳定性堪比本地。
    • 统一管理：所有人共用一套依赖，版本绝对一致。

2. 前置条件

  • Helm 版本：需要 Helm v3.8.0 或更高版本（目前已默认开启 OCI 支持）。
  • 仓库支持：需要一个支持 OCI 的仓库，推荐 Harbor 2.0+。

3. 实战操作指南

假设我们要把一个基础组件 common-lib 推送到内网 Harbor，并在业务 Chart 中引用它。

第一步：登录 OCI 仓库

这和 docker login 一模一样：

1
2
3

helm registry login harbor.example.com \
  --username <用户名> \
  --password <密码>

第二步：推送 Chart 到 OCI 仓库

先打包，再推送：

1
2
3
4
5

# 1. 打包 Chart
helm package charts/common-lib

# 2. 推送 (假设打包出了 common-lib-1.0.0.tgz)
helm push common-lib-1.0.0.tgz oci://harbor.example.com/my-project/charts

注意：推上去后，它的地址就是 oci://harbor.example.com/my-project/charts/common-lib

第三步：在业务 Chart 中引用依赖

编辑你的业务 Chart 的 Chart.yaml，注意 repository 字段的写法：

1
2
3
4
5

dependencies:
  - name: common-lib
    version: 1.0.0
    # 关键点：使用 oci:// 前缀，且不包含 chart 名字本身
    repository: oci://harbor.example.com/my-project/charts

重点说明：对于 OCI 依赖，repository URL 不应该包含 chart 的名字，只写到目录层级即可。Helm 会自动把 name 拼接到 URL 后面去查找。

第四步：更新依赖与 Git 忽略

运行以下命令时：

1

helm dependency update .

你会发现 Helm 仍然会将 .tgz 文件下载到本地的 charts/ 目录下。

请不要惊慌，这是正常的！ Helm 需要把这些文件下载下来，解压读取里面的模板，才能帮你生成最终的 Kubernetes YAML 文件。这就像你做饭必须先把菜从冰箱（OCI 仓库）拿出来放在案板上（本地目录）一样。

关键在于：不要把这些下载下来的文件提交到 Git！

我们需要配置 .gitignore 文件来忽略它们：

1
2
3

# 在项目根目录的 .gitignore 文件中添加：
charts/*.tgz
charts/*.lock

这样一来：

  1. 本地开发时：helm dependency update 下载依赖，你能正常部署调试。
  2. 提交代码时：Git 会自动无视这些 .tgz 文件，你的代码库依然干净。
  3. CI/CD 部署时：流水线先运行 helm dependency update 临时拉取依赖，然后立即部署，用完即焚。

懒人技巧：自动更新依赖

如果你觉得每次都要手动敲 helm dependency update 太麻烦，或者在 CI/CD 脚本里想少写一行命令，Helm 其实提供了一个自动挡开关。

你可以在 install、upgrade 或 template 命令中直接加上 --dependency-update 参数（可以简写为 --dep-up）。

示例：

1
2
3
4
5
6
7
8

# 安装时自动拉取依赖
helm install my-release . --dependency-update

# 升级时自动拉取依赖
helm upgrade my-release . --dependency-update
```bash
# 渲染模板时自动拉取依赖
helm template . --dependency-update

这样，Helm 会在执行主任务之前，先自动帮你把 charts/ 目录下的依赖包更新好。

Golang SDK 支持

如果你是在开发自己的平台或工具，使用 Helm 的 Golang SDK (helm.sh/helm/v3/pkg/action)，同样支持这个功能。

你只需要在初始化 Action 结构体后，将 DependencyUpdate 字段设置为 true 即可。

package main

import (
    "log"
    "os"

    "helm.sh/helm/v3/pkg/action"
    "helm.sh/helm/v3/pkg/cli"
)

func main() {
    settings := cli.New()
    actionConfig := new(action.Configuration)
    // 初始化 actionConfig ...

    // 1. 安装场景
    client := action.NewInstall(actionConfig)
    client.ReleaseName = "my-release"
    client.Namespace = "default"
    
    // 开启自动更新依赖
    client.DependencyUpdate = true 

    // 执行安装
    _, err := client.Run(nil, "./my-chart", nil)
    if err != nil {
        log.Fatal(err)
    }
    
    // 2. 升级场景
    upgradeClient := action.NewUpgrade(actionConfig)
    upgradeClient.DependencyUpdate = true
}

4. 总结

方案稳定性Git 仓库体积复杂度推荐场景
远程 HTTP Pull低小低仅限个人测试
本地打包 (tgz)高大 (存二进制)中简单项目，无 OCI 设施
内网 OCI 仓库高小中企业级生产环境 (强烈推荐)

结论：如果你有内网 Harbor，OCI 模式是最佳实践。它完美解决了“不依赖公网”和“Git 仓库不膨胀”这两个看似矛盾的需求。
