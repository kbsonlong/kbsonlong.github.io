Kubelet 核心功能与启动流程解析

简介

Kubelet 是 Kubernetes 集群中每个 Node 节点上运行的核心组件，扮演着“节点管家”的角色。它负责接收并执行 Master 节点（具体来说是 kube-apiserver）下发的指令，管理 Pod 的生命周期，确保节点上的容器按照预期状态运行。

Kubelet 的核心职责包括：

  • Pod 管理：根据 kube-apiserver 或静态 Pod 定义，创建、销毁和管理 Pod 的生命周期。
  • 容器健康检查：通过 Liveness Probe 和 Readiness Probe 监控容器的健康状况，并根据结果进行相应的处理（如重启容器）。
  • 容器资源监控：通过内嵌的 cAdvisor 收集容器和节点的资源使用情况（如 CPU、内存、磁盘、网络），并上报给 metrics-server，为 HPA 等组件提供数据支持。
  • 存储卷管理：负责为 Pod 挂载和卸载存储卷（Volume）。
  • 节点状态上报：定期向 kube-apiserver 汇报本节点的状态，包括资源使用情况、运行中的 Pod 列表等。

本文将深入分析 Kubelet 的源码，详细探究其从启动到创建第一个容器的完整流程，并解析其核心工作循环和指标计算机制。

入口点与初始化

// cmd/kubelet/kubelet.go

func main() {
	command := app.NewKubeletCommand()
	code := cli.Run(command)

main 函数的核心是调用 app.NewKubeletCommand() 来创建一个 Cobra 命令行应用。Cobra 是一个流行的 Go 语言库，用于构建现代化的命令行界面。这个 command 对象封装了 Kubelet 的所有启动逻辑，包括参数解析、配置加载和服务的最终运行。

cli.Run(command) 负责执行这个 Cobra 命令，启动 Kubelet 的核心服务。让我们深入到 app.NewKubeletCommand() 内部，看看 Kubelet 是如何被构建和启动的。该函数位于 cmd/kubelet/app/server.go。

NewKubeletCommand 的核心逻辑可以概括为以下几个步骤：

  1. 创建 Kubelet 标志和配置：

    • options.NewKubeletFlags(): 创建用于存储命令行标志的结构体。
    • options.NewKubeletConfiguration(): 创建 Kubelet 的配置对象，其中包含了大部分可配置的参数，并设置了默认值。

  2. 定义 Cobra 命令：

    • 创建一个 cobra.Command 实例。
    • 其核心是 Run 函数，当执行 kubelet 命令时，这个函数内的逻辑将被触发。

  3. 执行 Run 函数：

    • Run 函数是 Kubelet 启动的真正入口。它负责协调整个初始化过程。
    • 它调用 Run(ctx, kubeletServer, kubeletDeps, ...) 来启动 Kubelet 服务。

  4. 构建依赖 (KubeletDeps)：

    • 在调用 Run 之前，它会构建一个 kubeletServer 对象，该对象封装了 Kubelet 的标志和配置。
    • 然后调用 UnsecuredDependencies(&kubeletServer, ...) 来创建 Kubelet 运行所需的核心依赖项 (kubeletDeps)。这些依赖包括：
      • CloudProvider: 云厂商接口。
      • Mounter: 存储卷挂载器。
      • Subpather: SubPath 功能的实现。
      • OOMAdjuster: OOM 分数调整器。
      • OSInterface: 操作系统接口。
      • ContainerManager: 容器管理器。
      • CAdvisorInterface: cAdvisor 接口，用于获取指标。
      • StatsProvider: 容器和 Pod 的统计信息提供者。

  5. 启动 Kubelet：

    • 最终，Run 函数会调用 RunKubelet(kubeletServer, kubeletDeps, ...)。
    • RunKubelet 进一步调用 createAndInitKubelet。
    • 在 createAndInitKubelet 内部，kubelet.NewMainKubelet(...) 被调用，这会创建并初始化一个 Kubelet 对象。这个对象是 Kubelet 的核心，包含了所有管理 Pod 和容器所需的状态和方法。

核心工作循环 (syncLoop)

Kubelet 的初始化完成后，便会进入其核心的无限循环 syncLoop。这个循环是 Kubelet 的“心脏”，负责监听各种事件源，并将 Pod 的“期望状态”与节点上的“实际状态”进行同步。syncLoop 的实现位于 pkg/kubelet/kubelet.go。

syncLoop 本身是一个外层循环，它主要负责处理运行时错误和维持循环的持续运行。真正的事件处理逻辑位于 syncLoopIteration 函数中，该函数通过一个 select 语句来监听和处理来自多个 Channel 的事件。

// pkg/kubelet/kubelet.go

func (kl *Kubelet) syncLoopIteration(configCh <-chan kubetypes.PodUpdate, handler SyncHandler,
	syncCh <-chan time.Time, housekeepingCh <-chan time.Time, plegCh <-chan *pleg.PodLifecycleEvent) bool {
	select {
	case u, open := <-configCh:
		// 来自 kube-apiserver、静态 Pod 文件或 HTTP 的配置变更
		// ...
	case e := <-plegCh:
		// 来自 PLEG (Pod Lifecycle Event Generator) 的事件
		// ...
	case <-syncCh:
		// 定期同步所有 Pod
		// ...
	case <-housekeepingCh:
		// 定期清理工作
		// ...
	case update := <-kl.livenessManager.Updates():
		// 来自存活探针 (Liveness Probe) 的结果
		// ...
	}
	return true
}

下面我们来详细解析 syncLoopIteration 监听的几个关键事件源：

  1. configCh (配置变更)

    • 来源：这个 Channel 接收来自 kube-apiserver、静态 Pod 文件目录或 HTTP 端点的 Pod 配置更新。
    • 操作：当收到更新时，Kubelet 会根据事件的类型（ADD、UPDATE、REMOVE 等）调用相应的 SyncHandler 方法（如 HandlePodAdditions、HandlePodUpdates）。这些方法会将 Pod 的变更信息更新到 Kubelet 的内部缓存 podManager 中，并触发一次异步的 Pod 同步（dispatchWork）。

  2. plegCh (Pod 生命周期事件)

    • 来源：PLEG (Pod Lifecycle Event Generator) 是 Kubelet 的一个重要组件，它负责监控节点上容器的运行时状态，并生成 Pod 生命周期事件。例如，当一个容器启动或死亡时，PLEG 就会向 plegCh 发送一个事件。
    • 操作：收到 PLEG 事件后，Kubelet 会更新其内部的运行时缓存，并触发对相关 Pod 的同步（HandlePodSyncs），以确保 Pod 的状态与容器的实际状态保持一致。

  3. syncCh (定期同步)

    • 来源：这是一个定时触发的 Channel，默认每秒触发一次。
    • 操作：当收到 syncCh 事件时，Kubelet 会检查所有需要同步的 Pod（getPodsToSync），并将它们分派给 SyncHandler 进行处理（HandlePodSyncs）。这确保了即使没有外部事件，Kubelet 也会定期检查和同步所有 Pod 的状态。

  4. housekeepingCh (定期清理)

    • 来源：这是一个定时触发的 Channel，用于执行定期的清理任务。
    • 操作：Kubelet 会执行一些清理工作，例如清理不再需要的 Pod 目录、删除孤儿 Pod 等。

  5. livenessManager.Updates() (存活探针)

    • 来源：存活探针（Liveness Probe）的结果会通过这个 Channel 发送给 syncLoop。
    • 操作：如果一个容器的存活探针失败，livenessManager 会发送一个更新，syncLoop 在收到后会触发对该 Pod 的同步，这通常会导致 Kubelet 杀死并重启该容器。

Pod 的生命周期管理 (syncPod)

syncPod 函数是 Kubelet 中负责同步单个 Pod 状态的核心。每当 syncLoop 检测到需要对一个 Pod 进行同步时，无论是通过配置变更、PLEG 事件还是定期检查，最终都会调用 syncPod 来执行实际的同步操作。这个函数位于 pkg/kubelet/kubelet.go，它是一个庞大而复杂的函数，包含了 Pod 生命周期的所有管理逻辑。

syncPod 的主要职责是确保 Pod 的“实际状态”与 pod.Spec 中定义的“期望状态”保持一致。它通过一系列步骤来完成这个任务，包括创建和销毁容器、挂载和卸载卷、更新 Pod 状态等。

// pkg/kubelet/kubelet.go

func (kl *Kubelet) syncPod(o syncPodOptions) error {
	// ...

	// 第一步：如果 Pod 需要被杀死，立即执行
	if updateType == kubetypes.SyncPodKill {
		// ... 执行杀死 Pod 的逻辑 ...
		return nil
	}

	// 第二步：计算 Pod 的状态
	apiPodStatus := kl.generateAPIPodStatus(pod, podStatus)

	// 第三步：更新 Pod 状态到 statusManager
	kl.statusManager.SetPodStatus(pod, apiPodStatus)

	// 第四步：如果 Pod 不应该运行，则杀死它
	if podShouldnotBeRunning(pod) {
		// ...
		return nil
	}

	// 第五步：为静态 Pod 创建 Mirror Pod
	if kubetypes.IsStaticPod(pod) {
		// ...
	}

	// 第六步：创建 Pod 的数据目录
	if err := kl.makePodDataDirs(pod); err != nil {
		// ...
	}

	// 第七步：等待 Volume 挂载
	if !kl.podVolumesExist(pod.UID) {
		// ...
	}

	// 第八步：获取镜像拉取密钥
	pullSecrets, err := kl.getPullSecretsForPod(pod)

	// 第九步：调用容器运行时 (CRI) 的 SyncPod
	result := kl.containerRuntime.SyncPod(pod, podStatus, pullSecrets, kl.backOff)

	// ...
	return nil
}

syncPod 的核心步骤

  1. 处理 Pod 终止 (SyncPodKill)

    • 如果 syncPod 被调用时，updateType 为 SyncPodKill，说明这个 Pod 需要被立即终止。Kubelet 会调用 killPod 方法来停止 Pod 中的所有容器。

  2. 生成并更新 Pod 状态

    • Kubelet 会调用 generateAPIPodStatus 来根据容器的当前状态生成一个新的 v1.PodStatus。
    • 然后，它会将这个新的状态通过 statusManager 异步地更新到 kube-apiserver。

  3. 判断 Pod 是否应该运行

    • podShouldnotBeRunning 函数会检查 Pod 是否处于 Succeeded 或 Failed 状态，或者是否已经被删除。如果 Pod 不应该再运行，Kubelet 会调用 killPod 来清理它。

  4. 创建数据目录和挂载卷

    • Kubelet 会为 Pod 创建所需的数据目录（如 pods/<podUID>/volumes 和 pods/<podUID>/plugins）。
    • 它还会确保 Pod 所需的存储卷（Volume）已经被挂载和准备就绪。

  5. 调用容器运行时 (CRI)

    • 这是 syncPod 中最核心的一步。Kubelet 会调用容器运行时的 SyncPod 方法。这个调用会将 Pod 的期望状态（pod.Spec）传递给容器运行时（如 containerd 或 CRI-O）。
    • 容器运行时会负责：
      • 拉取 Pod 所需的镜像。
      • 创建和启动新的容器。
      • 停止和删除不再需要的容器。
      • 根据 Pod 的 restartPolicy 重启失败的容器。

Pod 的创建、更新和删除流程

  • 创建 Pod

    1. 用户通过 kubectl 或其他客户端创建一个新的 Pod 对象。
    2. kube-apiserver 将 Pod 信息存入 etcd，并通知 Kubelet。
    3. Kubelet 的 syncLoop 通过 configCh 收到 ADD 事件。
    4. HandlePodAdditions 将 Pod 添加到 podManager 并调用 dispatchWork。
    5. podWorkers 最终调用 syncPod。
    6. syncPod 调用容器运行时的 SyncPod，创建沙箱和容器。

  • 更新 Pod

    • Pod 的大部分字段是不可变的，但像 pod.Spec.containers[*].image 这样的字段可以被更新。
    • 当 Pod 被更新时，Kubelet 会收到一个 UPDATE 事件，并再次调用 syncPod。
    • syncPod 会再次调用容器运行时的 SyncPod，容器运行时会比较当前状态和新状态，并执行相应的操作（例如，停止旧的容器并启动新的容器）。

  • 删除 Pod

    1. 用户删除一个 Pod。
    2. kube-apiserver 会在 Pod 对象上设置一个 deletionTimestamp，并通知 Kubelet。
    3. Kubelet 收到 UPDATE 事件（因为 deletionTimestamp 被设置了）。
    4. syncPod 会检测到 deletionTimestamp，并开始优雅地终止 Pod。
    5. Kubelet 会调用容器运行时的 SyncPod 来停止容器，并执行清理工作（如卸载卷）。
    6. 一旦所有清理工作完成，Kubelet 会从其内部状态中移除该 Pod，并最终从 kube-apiserver 中删除该 Pod 对象。

指标计算流程 (cAdvisor)

Kubelet 的一个核心职责是监控节点上容器的资源使用情况，并将这些指标信息上报给 Kubernetes 的监控系统。这个功能主要由 cAdvisor 来实现，它是一个开源的容器监控工具，被直接集成到了 Kubelet 的二进制文件中。

指标的收集与暴露

Kubelet 内部有一个 StatsProvider 接口，它为 Kubelet 的其他组件提供了一个统一的获取指标的入口。StatsProvider 的实现依赖于 cAdvisor。

当外部组件（如 metrics-server）需要获取节点的指标时，它会访问 Kubelet 的 API 端点。Kubelet 提供了多个用于暴露指标的端点：

  • /stats/summary：这是最重要的一个端点。它提供了一个聚合的、详细的节点、Pod 和容器级别的资源使用摘要。metrics-server 就是通过这个端点来获取数据，并将其转换为 custom.metrics.k8s.io 和 external.metrics.k8s.io API，以供 HPA 控制器使用。
  • /metrics/cadvisor：这个端点以 Prometheus 的格式暴露了由 cAdvisor 收集的原始指标。这对于使用 Prometheus 进行监控和告警非常有用。
  • /metrics/resource：这个端点提供了用于调度的资源指标，例如节点上可分配的资源。

指标收集的周期控制

cAdvisor 的数据收集周期是由 Kubelet 的一个配置参数控制的，这个机制保证了 Kubelet 能够以可预测的频率获取到最新的容器指标。

核心控制参数：--housekeeping-interval

cAdvisor 的数据收集间隔由 Kubelet 的启动参数 --housekeeping-interval 控制。

  • 默认值：Kubelet 中该参数的默认值为 10 秒。
  • 作用：它决定了 cAdvisor 为每个容器独立执行指标收集的频率。值得注意的是，cAdvisor 内部有两种 housekeeping：一种是用于发现新容器的全局任务（周期较长，如1分钟），另一种是为每个容器收集指标的独立任务，后者由该参数控制。

代码实现追溯

要理解这个间隔是如何生效的，我们需要追溯代码的调用链。旧版本的 Kubelet/cAdvisor 可能采用一个全局 Ticker，但新版本的实现更为精细，它为每个容器启动一个独立的收集 goroutine。

  1. Kubelet 设置 cAdvisor 参数 (the “hack”)

    • 在 Kubelet 的入口 cmd/kubelet/app/server.go 的 NewKubeletCommand 函数中，有一段被标记为“临时 hack”的代码：
      1
2

      // cmd/kubelet/app/server.go
flag.Set("housekeeping_interval", kubeletFlags.HousekeepingInterval.Duration.String())
    • 这行代码的作用是，将 Kubelet 自己的 --housekeeping-interval 参数值，强制设置给 cAdvisor 库内部定义的一个同名全局标志 (flag)。这是 Kubelet 向其内嵌的 cAdvisor 传递配置的一种方式。

  2. cAdvisor 容器级指标收集 cAdvisor 的指标收集由 manager.go 和 container.go 协同完成。manager.go 负责全局容器发现和管理，而 container.go 负责单个容器的指标收集。

    • 全局 Housekeeping (manager.go)：manager.go 中的 Start 方法会启动一个 globalHousekeeping goroutine，它以一个独立的周期（globalHousekeepingInterval，默认 1 分钟）运行，主要用于检测新容器的出现，而不是高频次地收集现有容器的指标。

    • 容器级 Housekeeping (container.go)：真正的指标收集由 containerData 结构体中的 housekeeping 方法驱动，每个容器实例都会有一个独立的 housekeeping goroutine。

      • 初始化：newContainerData 函数在创建 containerData 时，会使用上一步设置的全局 HousekeepingInterval 标志来初始化每个容器自己的 housekeepingInterval 字段。
      • 启动：containerData.Start() 方法会为每个容器启动一个 housekeeping goroutine。
      • 执行循环：housekeeping 方法内部使用 time.Timer 来周期性地触发指标收集。nextHousekeepingInterval() 方法决定了下一次执行的间隔，其基准值就是 HousekeepingInterval。
      • 数据采集：housekeepingTick 函数最终会调用 updateStats，后者通过 cd.handler.GetStats() 从容器运行时接口（CRI）或 cgroup 文件系统获取原始数据。

func (cd *containerData) housekeeping() {
    // ...
    // 使用 Timer 而非 Ticker，因为间隔可能是动态的
    houseKeepingTimer := cd.clock.NewTimer(0 * time.Second)
    defer houseKeepingTimer.Stop()
    for {
        // housekeepingTick 会阻塞直到 Timer 触发
        if !cd.housekeepingTick(houseKeepingTimer.C(), longHousekeeping) {
            return
        }
        // ...
        // 重置下一次执行的 Timer
        houseKeepingTimer.Reset(cd.nextHousekeepingInterval())
    }
}

指标的存储 (InMemoryCache)

cAdvisor 采集到的指标并不会被持久化到磁盘，而是存储在一个高效的内存缓存中。这个组件名为 InMemoryCache，其实现位于 vendor/github.com/google/cadvisor/cache/memory/memory.go。

核心机制：

  1. 缓存结构：InMemoryCache 为每个容器（包括根容器，即节点本身）维护一个独立的、固定大小的环形缓冲区（Ring Buffer）。这个缓冲区用于存储最近一段时间内的 info.ContainerStats 时间序列数据。

  2. 数据写入：在 container.go 的 updateStats 函数成功获取到指标后，会调用 cd.memoryCache.AddStats() 方法。这个方法将最新的指标样本和时间戳添加到对应容器的环形缓冲区中。

  3. 存储策略：缓存默认会存储过去 60 秒的指标数据（这个值是硬编码在 memory.New 函数中的）。当新的指标数据被写入时，如果缓冲区已满，最旧的数据点将被覆盖。这种策略确保了内存占用的可预测性和稳定性。

  4. 数据读取：当外部请求（如 metrics-server 访问 /stats/summary 端点）需要指标数据时，Kubelet 的 StatsProvider 会调用 InMemoryCache 的 RecentStats 方法。该方法从环形缓冲区中提取指定时间范围内的指标数据，用于后续的聚合和计算。

通过这种内存缓存机制，cAdvisor 能够在不引入磁盘 I/O 开销的情况下，高效地为 Kubelet 提供短期、高分辨率的容器性能指标。

总结

本文深入剖析了 Kubelet 作为 Kubernetes 节点代理的核心功能和内部机制。我们从 Kubelet 的入口点 main 函数开始，逐步跟踪了其复杂的初始化过程，了解了 app.NewKubeletCommand 如何构建 Kubelet 的配置和依赖，并最终通过 RunKubelet 和 createAndInitKubelet 创建出核心的 Kubelet 实例。

随后，我们详细探讨了 Kubelet 的“心脏”——syncLoop 核心工作循环。这个事件驱动的循环通过 syncLoopIteration 监听来自 kube-apiserver 的配置变更、PLEG 的容器生命周期事件、定时同步以及 Liveness Probe 结果等多种事件源，确保节点上的 Pod 状态与期望状态保持一致。

在 Pod 生命周期管理方面，我们聚焦于 syncPod 函数。该函数是 Kubelet 同步单个 Pod 状态的关键，负责处理 Pod 的创建、更新和删除。syncPod 通过调用容器运行时的 SyncPod 方法，将 Kubelet 的指令转化为实际的容器操作，从而实现对 Pod 容器的精细化管理。

最后，我们分析了 Kubelet 的指标计算流程，重点介绍了内嵌的 cAdvisor。cAdvisor 负责从 cgroup 文件系统和内核接口收集容器和节点的资源使用数据，并在 Kubelet 启动时进行初始化和启动。Kubelet 通过 StatsProvider 接口将这些指标暴露给外部组件，例如 metrics-server 通过 /stats/summary 端点获取聚合指标，为 HPA 等控制器提供数据支持。

通过对 Kubelet 源码的深入分析，我们不仅理解了其各个组件的职责，更重要的是，掌握了 Kubelet 如何协同工作，确保 Kubernetes 集群中 Pod 的稳定运行和高效管理。Kubelet 的设计体现了 Kubernetes 强大的自愈能力和可扩展性，是构建弹性云原生应用的关键基石。
