Helm Charts 依赖管理

在 Helm Chart 的开发和维护过程中，我们经常会遇到一个问题：依赖包（Dependencies）是应该打包到本地，还是在部署时远程拉取？

作为一名资深 SRE，我的建议是：生产环境务必打包到本地。

1. 两种模式对比

我们可以用“做饭”来打个比方：

1.1 远程 Pull (现用现买)

  • 原理：在 Chart.yaml 中声明依赖，部署时通过网络下载。
  • 比喻：想做饭了才去菜市场买菜。
  • 风险：
    • 如果菜市场关门了（远程仓库宕机），你这顿饭就做不成了。
    • 如果去菜市场的路堵了（网络不通），你也做不成。
    • 哪怕只是想做个测试，也得跑一趟菜市场。

1.2 打包到本地 (买好存冰箱) 【推荐】

  • 原理：使用 helm dependency update 将依赖包下载到 Chart 目录下的 charts/ 文件夹中，并提交到 Git 仓库。
  • 比喻：提前买好菜存在冰箱里。
  • 优势：
    • 稳定性高：不管外面刮风下雨（断网、仓库故障），你都能随时做饭。
    • 版本可控：你存的是什么版本，用的就是什么版本，不会因为远程仓库悄悄更新而导致兼容性问题。
    • 离线部署：在完全隔离的内网环境也能轻松部署。

2. 实战操作指南

假设你的 Chart 需要依赖 Redis。

第一步：声明依赖

编辑 Chart.yaml：

1
2
3
4

dependencies:
  - name: redis
    version: 17.3.14
    repository: https://charts.bitnami.com/bitnami

第二步：下载依赖（进货）

在你的 Chart 根目录下运行：

1

helm dependency update .

运行后，你会发现多了一个 charts/ 目录，里面有一个 redis-17.3.14.tgz 文件。

第三步：提交代码

将 charts/*.tgz 文件连同你的代码一起提交到 Git 仓库。

1
2

git add charts/
git commit -m "chore: update helm dependencies"

3. 总结

为了保证生产环境的绝对稳定和可复现性，请务必养成将 Helm 依赖打包到本地的好习惯。这能帮你规避 90% 因网络或上游仓库问题导致的部署失败。
